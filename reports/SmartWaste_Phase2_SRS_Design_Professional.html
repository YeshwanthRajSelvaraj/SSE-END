Phase 2 / Design Baseline

1. Overview & Scope

An IoT-based waste management platform in which smart bins periodically send fill level, location, temperature and sensor status; the platform stores and analyzes the data, generates optimized collection routes, and allows administrators to assign vehicles and drivers.

Security objective: preserve the confidentiality, integrity and availability of device identities, telemetry, locations, routes, operational data and security evidence while keeping the design consistent across subsequent examination phases.
Core data
Fill level, location, temperature, sensor status and timestamps.
Core operations
Device management, telemetry processing, route optimization, assignment and monitoring.
Security focus
Sensor spoofing, location manipulation, unauthorized route modification, availability, device authentication and API security.

System boundary

In scope: web interface, API layer, authentication and RBAC, device registration/authentication, telemetry ingestion and validation, route optimization, vehicle/driver management, audit logging, security alerts and container-ready deployment. Out of scope: physical manufacture of bins, commercial mapping contracts and production municipal infrastructure.

7. Secure System Architecture

A layered modular architecture separates presentation, API entry, identity enforcement, domain services, data access and persistence. Route optimization is isolated from the external API boundary, while audit and alert handling remains a distinct cross-cutting capability.

10. Trust Boundaries

A trust boundary is placed wherever information crosses from a less-trusted zone into a more-trusted processing or storage zone. Each boundary is therefore a direct candidate for threat modeling and security controls.

Figure 5. Trust boundaries for the SmartWaste system.
BoundaryCrossingMain risksControls
TB-1IoT network → application/APIDevice spoofing, telemetry tampering, flooding.TLS, device authentication, schema/range validation, rate limiting, replay/sequence checks where applicable.
TB-2Browser → APICredential theft, broken authorization, API abuse.TLS, authentication, RBAC, validation, rate limiting and safe errors.
TB-3Application → databaseUnauthorized reads/writes, secret exposure.Least privilege, parameterized queries, network restriction, secret management.
TB-4Application → runtime/KubernetesExcessive privilege, exposed services.Non-root containers, restricted ports, resource limits and restricted service exposure.

11. Critical Information Flows

IF-01 · Bin telemetry

Smart Bin → TLS/MQTT or HTTPS → API Gateway → device authentication → telemetry validation → telemetry store.

Controls: device identity, schema/range checks, timestamp/sequence checks and audit on rejection.

IF-02 · Collection route

Administrator → authenticated API → RBAC/object-level authorization → Route Service → validation/version check → database → audit → driver.

Controls: authentication, authorization, route versioning and audit logging.

IF-03 · Device credentials

Provisioned device identity → secure authentication → device registry → telemetry authorization.

Controls: secure provisioning, revocation/rotation and no hard-coded secrets.

IF-04 · Security events

Application/security services → structured audit events → controlled storage → monitoring/alerting.

Controls: restricted writes, retention, monitoring and no secret/token logging.

14. Acceptance Criteria & Final Design Baseline

IDAcceptance Criterion
AC-01A valid registered device can submit telemetry and the data appears in the dashboard/database.
AC-02An unknown or revoked device is rejected and the security event is recorded.
AC-03Telemetry with invalid fill level or impossible coordinates is rejected.
AC-04Only an authorized administrator can modify a route; an unauthorized role receives 403.
AC-05Route modifications create an auditable event with actor, resource and timestamp.
AC-06API abuse is rate-limited and responses do not expose stack traces or secrets.
AC-07The application builds and runs as a non-root Docker container.
AC-08Kubernetes deployment applies non-root security context and resource limits.

Approved baseline

Authenticated smart bins → validated telemetry → protected storage → route optimization → authorized vehicle/driver assignment → audited operations.
Security controls are applied at the trust boundaries, not only at the user interface.
