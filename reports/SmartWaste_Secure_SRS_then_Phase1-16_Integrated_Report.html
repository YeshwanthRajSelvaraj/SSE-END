SRS foundation

1. Introduction

1.1 Purpose

This Software Requirements Specification (SRS) defines the requirements for SmartWaste Secure, an IoT-based waste-management platform that receives smart-bin telemetry, validates and stores it, detects suspicious behaviour, generates optimized collection routes, and supports authorized vehicle and driver assignment.

1.2 Problem statement

Smart bins periodically send fill level, location, temperature and sensor status. The platform uses these measurements to support collection decisions and route optimization. The security problem is that the telemetry originates from devices and networks that cannot be assumed trustworthy. The system therefore has to protect both the device-to-platform boundary and the platform's high-impact operational functions.

1.3 Security challenges in the supplied problem

Sensor spoofing
False sensor measurements could change collection priority or status.
Location manipulation
Incorrect coordinates could lead to incorrect routes.
Unauthorized route modification
Unauthorized users could disrupt physical operations.
Availability
Flooding or resource exhaustion could block telemetry or routing.
Device authentication
Unknown or revoked devices must not be trusted.
API security
Protected APIs must resist broken authorization, abuse and data exposure.

1.4 Document conventions

FR = Functional Requirement; NFR = Non-Functional Requirement; SEC = Security Requirement; A = Asset; AC = Acceptance Criterion; HI = Hardware Interface; SI = Software/Communication Interface.

System definition

2. Overall Description

2.1 Product perspective

SmartWaste Secure is a layered application system consisting of an IoT/edge device layer, secure telemetry transport, backend API services, persistent storage, a route-optimization component and role-specific user interfaces. The system is intended for an academic laboratory environment and is designed so that IoT hardware can be simulated or prototyped without changing the logical requirements.

2.2 Major capabilities

CapabilityDescription
Device lifecycleRegister, activate, monitor and revoke smart bins.
TelemetryReceive and validate periodic fill, location, temperature and sensor-status data.
MonitoringShow current bin status, health, alerts and last-seen state.
Route optimizationGenerate collection routes from validated operational inputs.
Resource assignmentAssign vehicles and drivers to routes.
Route securityRestrict route modification to authorized administrators.
Security monitoringDetect anomalous telemetry and suspicious access.
AuditRecord security-sensitive and administrative events.

2.3 Operating environment

The academic baseline is designed to run on a laptop or laboratory host. The backend may use Docker, the message broker may use Mosquitto, the database may use PostgreSQL, and the application may be deployed locally with Minikube/Kubernetes in later phases.

2.4 User characteristics

Administrators are trusted operational users but are still subject to authorization and audit controls. Drivers require operational access but not administrative route modification privileges. Security auditors require evidence access without unnecessary modification privilege. Smart bins are treated as untrusted technical actors even after device authentication.

5.2 Device security requirements

  • The smart bin shall have a unique device identity.
  • Device identity shall be checked before telemetry is accepted.
  • Device credentials/keys shall not be hard-coded in public source files.
  • Where the secure element is used, private key material should remain in the secure element rather than ordinary firmware storage.
  • A revoked/disabled device shall be rejected even if it presents structurally valid telemetry.
  • The device shall have no permission to modify routes, read other devices' telemetry, or access the database directly.

5.3 Device reporting requirements

Each report should contain a device identifier, timestamp, message/sequence identifier where implemented, fill level, latitude, longitude, temperature and sensor/device status. The exact reporting interval is configuration data and shall be defined by the deployment profile rather than hard-coded into the SRS.

8.1 Authentication requirements

  • User authentication shall precede access to protected UI/API operations.
  • Smart-bin authentication shall precede accepted telemetry processing.
  • Authentication failures shall not reveal whether a credential or account exists beyond the minimum required response.
  • Device revocation shall be enforceable server-side.

8.2 Authorization requirements

  • Authorization shall be checked server-side on every protected operation.
  • Role checks shall be supplemented by object-level checks for specific routes and operational resources.
  • Drivers shall be denied route modification by default.
  • Security auditors shall have read-only access to audit evidence.

8.3 Audit requirements

At minimum, the system shall audit successful and failed login attempts, device authentication failures, route creation/modification/cancellation, privilege changes, device revocation, significant telemetry anomalies and rate-limit/security events. Logs shall exclude passwords, raw access tokens and private keys.

  • Telemetry shall be validated before persistence into trusted operational state.
  • Route updates shall use version/state checks to reduce stale or illegal updates.
  • Database queries shall use parameterized access patterns / ORM controls.
Operational rules

10. Business and Operational Rules

RuleBusiness / security rule
BR-01Fill level must be between 0 and 100 percent before it is accepted as trusted operational data.
BR-02Latitude must be within -90 to 90 degrees; longitude must be within -180 to 180 degrees.
BR-03A revoked or disabled device cannot submit accepted telemetry.
BR-04An authenticated driver cannot modify routes unless a separate explicit permission is granted; the default policy is deny.
BR-05Route modifications must pass route-state validation and create an audit event.
BR-06Security logs must not contain passwords, raw tokens or private keys.
BR-07Suspicious but syntactically valid telemetry may be retained as an anomaly/security event but must not be blindly trusted by route optimization.
BR-08A device can be taken out of service without deleting historical telemetry needed for audit or analysis.

10.1 Route decision policy

The route engine shall use validated application data. Raw unvalidated sensor payloads shall not be passed directly to route optimization. A suspicious measurement may be retained as evidence, but the operational decision path shall follow the defined trust policy.

System boundaries

11. Assumptions and Constraints

11.1 Assumptions

  • Smart bins have network connectivity sufficient to reach the secure telemetry endpoint.
  • Each device can maintain a unique identity/credential.
  • A route-optimization algorithm can operate on simulated or predefined coordinates in the laboratory.
  • Docker and a local Kubernetes distribution can be used for later deployment exercises.

11.2 Constraints

  • This SRS defines an academic laboratory system and does not claim production municipal deployment certification.
  • The exact hardware models are a proposed prototype baseline because the problem statement only specifies telemetry categories.
  • External mapping services are not assumed to be available; route optimization must have a laboratory fallback.
  • Real-world GPS spoofing cannot be fully eliminated through application software alone.

11.3 Out of scope

  • Manufacture and certification of municipal smart-bin hardware.
  • National-scale fleet management and production SLAs.
  • Autonomous vehicle control.
  • Government identity-provider integration.

Agile Process and Development Approach

6 Marks
Sub-part 1 — Select and justify an Agile approach.
The project uses a Hybrid Scrum + XP approach: Scrum supplies the delivery cadence (planning, daily Scrum, review, retrospective and backlog control), while XP practices supply engineering discipline for a security-critical IoT system (test-first development for security functions, continuous integration, peer review and refactoring). This is appropriate because security controls such as HMAC verification, replay detection, geofence validation and route authorization must evolve together with functional requirements.
